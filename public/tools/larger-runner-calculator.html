Larger runner calculator: is a bigger GitHub runner worth it?

A 4-core Linux runner costs twice as much per minute as the 2-core one. It only saves money if the job finishes in less than half the time. Enter a job's current duration and estimate how much of it scales with CPU cores.

Reading the result

Break-even speedup is the price ratio: how many times faster the job must finish for the bigger runner to cost the same. A 16-core Linux runner is $0.042 a minute, seven times the 2-core rate, so the job needs to be seven times faster just to break even. Few jobs scale that well.

Larger runners can still be worth paying for. Faster feedback on pull requests saves developer time, which usually costs more than CI. This calculator shows the CI side of that trade.

Estimating the share that scales

  • Scales well (70–90%): large compiles with parallel builds (make -j, Rust, C++, Gradle with parallelism on), and test suites sharded across cores.
  • Scales somewhat (30–60%): typical JavaScript or Python test suites with a parallel test runner.
  • Barely scales (0–20%): dependency installs, Docker pulls, network-bound integration tests, and single-threaded test runners.

The quickest way to know is to run the job once on the larger runner and compare. Each job is rounded up to a whole minute on every size, which is included here.

On a public repository?

Standard runners are free there and larger runners aren't. A larger runner on a public repository is pure added cost. The workflow checker flags it.

Want the real numbers instead of estimates?

Load GitHub's detailed usage report on the spendtron homepage for a chart of cost by workflow and runner. It's read in your browser and not uploaded. Or connect the GitHub App to price every job from real runs and get the fixes as a pull request. Both are free.
